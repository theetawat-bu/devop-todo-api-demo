# 🐳 Docker — ระดับ 5: มืออาชีพ

> **เป้าหมาย:** ดูแล supply chain ของ image ทั้งวงจร และตัดสินใจเชิงนโยบายให้ทีมได้
> **ต้องมีก่อน:** ผ่านระดับ 4
> **เวลาโดยประมาณ:** 2–5 วัน
> ระดับนี้หลายข้อ **ไม่มีคำตอบเดียว** — ผลลัพธ์ที่ต้องการคือเอกสารการตัดสินใจที่มีเหตุผลรองรับ

---

### D5.1 SBOM

**โจทย์:** สร้าง SBOM (รายการ dependency ทั้งหมดใน image) แล้วแนบไปกับ image ตอน push
**คำใบ้:** `docker buildx build --sbom=true --provenance=true --push` หรือใช้ `syft`
**ผ่านเมื่อ:** ดึง SBOM กลับมาอ่านได้ และตอบคำถามนี้ได้ภายใน 5 นาที — *"พรุ่งนี้มี CVE ใหม่ของ library X เราจะรู้ได้ยังไงว่า image ไหนที่ deploy อยู่ได้รับผลกระทบบ้าง"*

---

### D5.2 เซ็นและตรวจสอบลายเซ็น image

**โจทย์:** เซ็น image ด้วย cosign แล้ว verify
**คำใบ้:** `cosign generate-key-pair` → `cosign sign --key cosign.key ghcr.io/...` → `cosign verify --key cosign.pub ...`
**ผ่านเมื่อ:** verify ผ่าน และอธิบายได้ว่ากันการโจมตีแบบไหน (มีคนแอบ push image ปลอมทับ tag เดิมใน registry)
**ต่อยอด:** ลองใช้ keyless signing ผ่าน OIDC ของ GitHub Actions แทนการเก็บ key เอง

---

### D5.3 บังคับ policy ตอน deploy

**โจทย์:** ตั้งกฎในคลัสเตอร์ว่า **ห้าม** deploy image ที่ (ก) รันเป็น root (ข) ใช้ tag `latest` (ค) ไม่มีลายเซ็น
**คำใบ้:** Kyverno หรือ OPA Gatekeeper
**ผ่านเมื่อ:** ลอง apply manifest ที่ผิดกฎแล้วถูกปฏิเสธจริง พร้อมข้อความ error ที่คนอ่านแล้วเข้าใจว่าต้องแก้อะไร

---

### D5.4 ลดเวลา build ของทีมลง 30%

**โจทย์:** ทำให้ CI build เร็วขึ้นอย่างน้อย 30% แล้วเขียนสรุปว่าทำอะไรไปบ้าง
**คำใบ้:** registry cache (`type=registry`) แทน `type=gha`, แยก stage ที่เปลี่ยนน้อย, build เฉพาะ platform ที่ต้องใช้จริง, ตัด step ที่ซ้ำซ้อน
**ผ่านเมื่อ:** มีตัวเลขก่อน-หลังจากหน้า Actions จริง ไม่ใช่จากเครื่องตัวเอง

---

### D5.5 นโยบายการอัปเดต base image

**โจทย์:** ออกแบบว่าทีมจะอัปเดต base image ยังไง ให้ตอบได้ทั้ง 3 ข้อ — ใครรับผิดชอบ, ทุกกี่วัน, ถ้า base ใหม่ทำแอปพังจะรู้ตอนไหน
**คำใบ้:** Renovate/Dependabot + CI ที่ทดสอบจริง
**ผ่านเมื่อ:** มี PR อัตโนมัติเกิดขึ้นจริงเมื่อ base image มีเวอร์ชันใหม่ และ CI ตรวจให้ก่อน merge

---

### D5.6 ซ้อมกู้ระบบภายใต้เวลาจำกัด

**โจทย์:** สมมติ image ที่ deploy อยู่ใน production มี CVE ระดับ critical ต้องเปลี่ยนภายใน 30 นาที — เขียน runbook ทีละขั้น แล้วซ้อมทำจริง
**ผ่านเมื่อ:** ทำตาม runbook ของตัวเองได้สำเร็จ พร้อมจับเวลา และแก้ runbook ตรงจุดที่สะดุด

---

### D5.7 ตัดสินใจเรื่อง base image ให้ทั้งองค์กร

**โจทย์:** เขียน ADR (Architecture Decision Record) 1 หน้า เลือกระหว่าง `alpine` / `debian-slim` / `distroless` สำหรับบริการ Go ขององค์กร
**ต้องมีในเอกสาร:** เกณฑ์ที่ใช้ตัดสิน, ข้อมูลจริงที่วัดมา (ขนาด, จำนวน CVE, เวลา build), ทางเลือกที่ไม่ได้เลือกและเหตุผล, เงื่อนไขที่จะทำให้ต้องกลับมาทบทวน
**ผ่านเมื่อ:** คนที่ไม่ได้อยู่ในห้องตอนตัดสินใจ อ่านแล้วเข้าใจว่าทำไมถึงเลือกแบบนั้น

> เกร็ด: `alpine` ใช้ musl libc ไม่ใช่ glibc ซึ่งเคยทำให้บาง native module และ DNS resolver มีพฤติกรรมต่างจาก debian — ข้อนี้ควรอยู่ในเอกสารของคุณ
