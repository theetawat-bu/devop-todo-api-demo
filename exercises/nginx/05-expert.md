# 🌐 Nginx — ระดับ 5: มืออาชีพ

> **เป้าหมาย:** ตัดสินใจเชิงสถาปัตยกรรมเรื่อง edge layer ได้ และอธิบายเหตุผลให้ทีมฟังได้
> **ต้องมีก่อน:** ผ่านระดับ 4
> **เวลาโดยประมาณ:** 2–5 วัน
> ระดับนี้วัดผลด้วย **เอกสารและตัวเลข** ไม่ใช่แค่ config ที่รันผ่าน

---

### N5.1 zero-downtime reload ภายใต้โหลดจริง

**โจทย์:** ยิงโหลดต่อเนื่องแล้ว `nginx -s reload` ระหว่างนั้น
**ผ่านเมื่อ:** error เป็น 0 และอธิบายกลไกได้ — master สร้าง worker ใหม่ ส่วน worker เก่าปิดรับ connection ใหม่แต่ทำงานที่ค้างจนจบ
**ต่อยอด:** ลองทำให้ error ไม่เป็น 0 (เช่น `nginx -s stop` แทน `reload`) เพื่อเห็นความต่าง

---

### N5.2 แปลง config เป็น Ingress ให้ครบ

**โจทย์:** เอา config ทุกอย่างที่ทำมาตั้งแต่ระดับ 1–4 มาแปลงเป็น Ingress annotation
**ผลลัพธ์ที่ต้องได้:** ตาราง 3 คอลัมน์

| nginx directive | Ingress annotation | ทำไม่ได้ → ต้องใช้อะไรแทน |
| --- | --- | --- |

**ผ่านเมื่อ:** คอลัมน์ที่ 3 มีอย่างน้อย 3 รายการพร้อมทางออกที่เป็นรูปธรรม
คอลัมน์นี้แหละคือของจริง — มันบอกว่าคุณรู้ข้อจำกัดของ Ingress ไม่ใช่แค่ใช้เป็น

---

### N5.3 ADR เรื่อง rate limit

**โจทย์:** เขียนบันทึกการตัดสินใจ 1 หน้า ตอบว่าระบบของคุณควรตั้ง rate limit ที่ชั้นไหน
**ต้องมีในเอกสาร:**

- จำนวน replica ของ edge layer จริงในระบบคุณ และ limit ที่แท้จริงที่คำนวณได้ (`rate × replicas`)
- ความต้องการทางธุรกิจ (quota ต่อผู้ใช้? ต่อ IP? ต่อ API key?)
- ทางเลือกที่พิจารณาแล้วไม่เลือก พร้อมเหตุผล
- เงื่อนไขที่จะทำให้ต้องกลับมาทบทวน

**ผ่านเมื่อ:** มีตัวเลขจริงรองรับ เช่น *"ingress 3 replica × 10rps = 30rps ซึ่งเกิน SLA 20rps จึงต้องย้าย quota ไปทำที่แอปด้วย Redis"*
อ่านประกอบ: [docs/09 — จะตั้งค่าที่ชั้นไหนดี](../../docs/09-where-to-configure.md)

---

### N5.4 mTLS ระหว่าง proxy กับ backend

**โจทย์:** ให้ backend รับเฉพาะ connection ที่มี client certificate ที่ถูกต้อง
**คำใบ้:** สร้าง CA เอง → ออก cert ให้ nginx → ตั้ง `proxy_ssl_certificate` → ฝั่ง Node ใช้ `https.createServer({ requestCert: true, ca })`
**ผ่านเมื่อ:** ยิงตรงไปที่ backend โดยไม่มี cert แล้วถูกปฏิเสธ แต่ผ่าน nginx แล้วใช้ได้ปกติ

---

### N5.5 ซ้อมรับมือ traffic ผิดปกติ

**โจทย์:** จำลอง bot ยิง 1,000 rps จาก IP เดียว พร้อมกับผู้ใช้ปกติ 10 rps จากหลาย IP
**ผ่านเมื่อ:** ผู้ใช้ปกติได้ 200 เกิน 95% ขณะที่ bot โดน 429 — แล้วเขียนสรุปว่าจูนอะไรถึงได้ผลนี้ และผลข้างเคียงคืออะไร

---

### N5.6 ออกแบบ observability ของ edge layer

**โจทย์:** ตอบให้ได้ว่าถ้าเว็บช้า จะรู้ได้ยังไงว่าช้าที่ nginx, ที่ network, หรือที่แอป
**ต้องมี:** metric ที่ต้องเก็บ, alert ที่ต้องตั้ง (พร้อม threshold ที่มีเหตุผล), dashboard ที่ต้องมี
**คำใบ้:** `$request_time` vs `$upstream_response_time` คือกุญแจ — ผลต่างของสองค่านี้บอกว่าเวลาหายไปที่ไหน
**ผ่านเมื่อ:** มีคนอื่นในทีมอ่านแล้วใช้ debug ได้จริงโดยไม่ต้องถามคุณ

---

### N5.7 ตัดสินใจว่ายังต้องมี nginx ไหม

**โจทย์:** ระบบของคุณกำลังย้ายขึ้น Kubernetes — เขียนข้อเสนอว่าจะทำยังไงกับ nginx เดิม
**ทางเลือกที่ต้องพิจารณา:** ย้าย config ไป ingress-nginx / เปลี่ยนไป Gateway API / ใช้ service mesh / คง nginx ไว้เป็น sidecar
**ผ่านเมื่อ:** เลือกได้พร้อมเหตุผล และระบุ config ที่จะ "สูญหาย" ระหว่างย้ายพร้อมแผนรับมือ
