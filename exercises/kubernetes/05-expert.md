# ☸️ Kubernetes — ระดับ 5: มืออาชีพ

> **เป้าหมาย:** รับผิดชอบระบบใน production ได้ — ออกแบบ ป้องกัน กู้คืน และอธิบายให้ทีมเข้าใจ
> **ต้องมีก่อน:** ผ่านระดับ 4
> **เวลาโดยประมาณ:** 1–2 สัปดาห์
> ระดับนี้วัดที่ **เอกสาร ตัวเลข และการซ้อมจริง** ไม่ใช่ YAML ที่ apply ผ่าน

---

### K5.1 กำหนด SLO แล้วตั้ง alert จากมัน

**โจทย์:** นิยาม SLO ของ API เช่น *"99.5% ของ request ตอบภายใน 300ms ใน 30 วัน"* แล้วตั้ง alert จาก error budget
**ผ่านเมื่อ:** มี dashboard แสดง error budget ที่เหลือ และ alert ที่ดังเมื่อ **เผาเร็วผิดปกติ** ไม่ใช่ดังทุกครั้งที่มี error หนึ่งตัว
**สิ่งที่ต้องตอบได้:** ทำไม alert ที่ดังทุกครั้งที่มี 5xx ถึงเป็น alert ที่ไม่มีใครสนใจภายในสองสัปดาห์

---

### K5.2 Chaos engineering

**โจทย์:** ใช้ chaos-mesh หรือ litmus ทำการทดลอง 3 แบบ — ฆ่า pod สุ่ม, หน่วง network 500ms, ทำให้ DB ช้า
**ผ่านเมื่อ:** บันทึกได้ว่าแต่ละแบบผู้ใช้เห็นอะไร ระบบฟื้นเองได้ไหม ใช้เวลาเท่าไร แล้วแก้จุดที่ฟื้นไม่ได้
**เขียนสรุป:** อะไรที่คิดว่าจะรอดแต่ไม่รอด — ส่วนนี้มีค่าที่สุด

---

### K5.3 ซ้อมกู้คืนฐานข้อมูล

**โจทย์:** สำรองข้อมูล postgres แล้วลบ PVC ทิ้ง จากนั้นกู้กลับ
**ผ่านเมื่อ:** ข้อมูลกลับมาครบ พร้อมจับเวลา **RTO** (ใช้เวลากู้เท่าไร) และ **RPO** (ข้อมูลหายย้อนหลังกี่นาที)
**คำถามที่ต้องตอบ:** ตัวเลขสองตัวนี้ที่ได้ ธุรกิจรับได้ไหม ถ้าไม่ ต้องเปลี่ยนอะไร

---

### K5.4 นโยบายความปลอดภัยระดับคลัสเตอร์

**โจทย์:** ใช้ Kyverno หรือ OPA Gatekeeper บังคับกฎเหล่านี้กับทุก namespace

- ห้าม container รันเป็น root
- ทุก container ต้องมี `resources.requests` และ `limits`
- ห้ามใช้ image tag `latest`
- ต้องดึง image จาก registry ที่อนุญาตเท่านั้น

**ผ่านเมื่อ:** ลอง apply manifest ที่ผิดกฎแล้วถูกปฏิเสธ พร้อมข้อความที่บอกวิธีแก้ให้ผู้ใช้เข้าใจ

---

### K5.5 แผนอัปเกรดคลัสเตอร์

**โจทย์:** เขียนแผนอัปเกรด Kubernetes ขึ้นหนึ่ง minor version โดยไม่มี downtime
**ต้องมีในแผน:** ตรวจ API ที่ถูก deprecated (`kubectl-convert`, pluto), ลำดับ control plane → node, PDB ที่ต้องมีก่อน drain, เกณฑ์ยกเลิกและวิธีย้อนกลับ
**ผ่านเมื่อ:** ทำจริงบนคลัสเตอร์ทดสอบได้สำเร็จตามแผน

---

### K5.6 มัลติเทนแนนซี

**โจทย์:** ออกแบบให้ 3 ทีมใช้คลัสเตอร์เดียวกันโดยไม่รบกวนกัน
**ต้องมี:** namespace + ResourceQuota + LimitRange + NetworkPolicy + RBAC + Argo AppProject
**ผ่านเมื่อ:** พิสูจน์ได้ว่าทีม A ใช้ทรัพยากรจนเต็มโควตาแล้ว ทีม B ยังทำงานได้ปกติ

---

### K5.7 วิเคราะห์ต้นทุน

**โจทย์:** วัดว่า request จริงใช้ทรัพยากรเท่าไร แล้วปรับ `requests`/`limits` ให้พอดี
**คำใบ้:** ดูค่าจริงจาก Prometheus ย้อนหลังอย่างน้อย 1 สัปดาห์ — ใช้ p95 ไม่ใช่ค่าเฉลี่ย
**ผ่านเมื่อ:** ลดทรัพยากรที่จองได้โดยไม่กระทบ SLO และมีตัวเลขก่อน-หลัง
**อธิบายให้ได้:** ตั้ง `requests` ต่ำเกินไปอันตรายยังไง และตั้งสูงเกินไปเสียหายยังไง

---

### K5.8 เขียน runbook ที่คนอื่นใช้ได้จริง

**โจทย์:** เขียน runbook สำหรับ 3 เหตุการณ์ — API ตอบ 5xx เกิน 5%, DB ต่อไม่ได้, deploy แล้วพัง
**ผ่านเมื่อ:** **ให้เพื่อนร่วมทีมที่ไม่ได้เขียน runbook ทำตามแล้วแก้ปัญหาได้** โดยไม่ต้องถามคุณสักคำ
นี่คือเกณฑ์เดียวที่วัดคุณภาพ runbook ได้จริง

---

### K5.9 postmortem

**โจทย์:** เลือกเหตุการณ์หนึ่งจากการซ้อม chaos แล้วเขียน postmortem แบบไม่โทษคน
**ต้องมี:** timeline, ผลกระทบเชิงตัวเลข, สาเหตุราก (ถาม "ทำไม" 5 ครั้ง), สิ่งที่ทำงานได้ดี, action item ที่มีเจ้าของและกำหนดเวลา
**ผ่านเมื่อ:** action item ทุกข้อเป็นการแก้ระบบ ไม่ใช่ "ต้องระวังมากขึ้น"
