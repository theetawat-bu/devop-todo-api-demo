## C5.1 DORA metrics

ดึงข้อมูลจาก GitHub API:

```bash
# ความถี่ในการ deploy (30 วันล่าสุด)
gh api "repos/:owner/:repo/deployments?environment=production&per_page=100" \
  | jq '[.[] | select(.created_at > (now - 2592000 | todate))] | length'

# lead time: commit → deploy
gh api "repos/:owner/:repo/actions/workflows/deploy-k8s.yml/runs?per_page=50" \
  | jq -r '.workflow_runs[] | "\(.head_sha) \(.created_at) \(.updated_at)"'
```

| ระดับ | Deploy Frequency | Lead Time | Change Failure Rate | Time to Restore |
| --- | --- | --- | --- | --- |
| Elite | หลายครั้งต่อวัน | < 1 ชม. | 0-15% | < 1 ชม. |
| High | รายวัน–รายสัปดาห์ | 1 วัน–1 สัปดาห์ | 16-30% | < 1 วัน |
| Medium | รายสัปดาห์–รายเดือน | 1 สัปดาห์–1 เดือน | 16-30% | 1 วัน–1 สัปดาห์ |
| Low | น้อยกว่ารายเดือน | > 1 เดือน | 16-30% | > 1 สัปดาห์ |

**สิ่งที่ต้องเข้าใจ: ตัวชี้วัด 4 ตัวนี้แบ่งเป็นสองคู่ที่ถ่วงดุลกัน**

```
ความเร็ว (frequency, lead time)  ⟷  ความมั่นคง (failure rate, restore time)
```

**ถ้าดูตัวเดียวจะได้พฤติกรรมที่ผิด:** ไล่ deploy frequency อย่างเดียว → คุณภาพตก
ไล่ change failure rate อย่างเดียว → ทีมกลัวจนไม่กล้า deploy

**ข้อค้นพบสำคัญจากงานวิจัย DORA:** ทีมที่เก่งจริง**ดีทั้งสี่ตัวพร้อมกัน** — ความเร็วกับความมั่นคงไม่ได้ขัดแย้งกัน
ทีมที่ deploy บ่อยจะ deploy ทีละนิด ซึ่งพังน้อยกว่าและแก้ง่ายกว่า

**เกณฑ์ผ่าน:** มีตัวเลขจริง + เลือก 1 ตัวมาปรับปรุงพร้อมสมมติฐานว่าอะไรคือคอขวด

## C5.2 กลยุทธ์ branch

| | Trunk-based | GitHub Flow | GitFlow |
| --- | --- | --- | --- |
| branch หลัก | main เท่านั้น | main + feature | main, develop, release, hotfix, feature |
| อายุ branch | < 1 วัน | 2-5 วัน | เป็นสัปดาห์ |
| ต้องมี feature flag | ✅ จำเป็น | บางครั้ง | ไม่ต้อง |
| รองรับหลายเวอร์ชันพร้อมกัน | ❌ | ❌ | ✅ |
| ความซับซ้อน | ต่ำ | ต่ำ | **สูง** |
| เหมาะกับ | ทีมที่ deploy บ่อย, เทสอัตโนมัติดี | **ทีมส่วนใหญ่** | ซอฟต์แวร์ที่ลูกค้าติดตั้งเอง |

**คำตอบสำหรับโปรเจกต์นี้: GitHub Flow + branch `dev` สำหรับ environment ทดสอบ**

```
feature/xxx → PR → main (production)
                └→ dev (สภาพแวดล้อมทดสอบบน cloud)
```

**GitFlow เกินความจำเป็นสำหรับ web app ส่วนใหญ่** — มันถูกออกแบบมาสำหรับยุคที่ release เป็นรายไตรมาส
และต้อง support หลายเวอร์ชันพร้อมกัน ถ้าคุณ deploy ได้ทุกวันและมีเวอร์ชันเดียวใน production คุณไม่ต้องการมัน

**"แล้ว hotfix ทำยังไง" (คำถามที่ต้องตอบให้ได้):**
ใน GitHub Flow → hotfix ก็คือ PR ปกติที่ merge เร็วกว่า ไม่ต้องมี branch ชนิดพิเศษ
**ถ้าเส้นทางปกติเร็วพออยู่แล้ว ก็ไม่ต้องมีเส้นทางพิเศษ** — และเส้นทางพิเศษที่ไม่ค่อยได้ใช้มักจะพังตอนที่ต้องใช้จริง

## C5.3 ความปลอดภัยของ pipeline

```yaml
# ❌ ไม่ปลอดภัย
- uses: actions/checkout@v4          # tag ถูกย้ายได้
- uses: some-random/action@master    # อันตรายมาก

# ✅ ปลอดภัย
- uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608 # v4.1.0
```

```yaml
permissions: {} # ปิดทุกอย่างที่ระดับ workflow

jobs:
  build:
    permissions: # เปิดเฉพาะที่ job นี้ต้องใช้
      contents: read
      packages: write
```

**ทำไมต้อง pin ด้วย SHA:** tag `v4` เป็นแค่ตัวชี้ที่เจ้าของ action ย้ายได้ตลอด
ถ้าบัญชีเจ้าของถูกยึด ผู้โจมตีย้าย tag `v4` ไปหาโค้ดร้าย → **ทุก repo ในโลกที่ใช้ `@v4` รันโค้ดนั้นทันที**
เคยเกิดขึ้นจริงกับ action ยอดนิยมมาแล้ว

**เรื่อง fork PR ที่ต้องรู้:**

| trigger | secret เข้าถึงได้ | อันตราย |
| --- | --- | --- |
| `pull_request` | ❌ | ปลอดภัย |
| **`pull_request_target`** | ✅ | **อันตรายมาก** — รัน workflow ของ base แต่ checkout โค้ดของ fork ได้ |

ถ้าจำเป็นต้องใช้ `pull_request_target` **ห้าม checkout โค้ดจาก PR** โดยเด็ดขาด

ตรวจสอบด้วย:

```bash
pip install zizmor && zizmor .github/workflows/
```

## C5.4 แผนย้ายไป GitOps

```markdown
# แผนย้ายจาก push-based ไป GitOps

## เฟส 1 (สัปดาห์ 1-2): เตรียม — ยังไม่กระทบใคร
- ติดตั้ง Argo CD ในคลัสเตอร์ dev
- สร้าง config repo แล้วก็อป manifest ปัจจุบันเข้าไป
- ตั้ง Application ในโหมด **manual sync** เพื่อดูว่า diff ตรงกับของจริงไหม
- เกณฑ์ผ่านเฟส: Argo แสดง "Synced" โดยไม่มี diff ที่ไม่คาดคิด

## เฟส 2 (สัปดาห์ 3): รันคู่ขนานที่ dev
- CI ยังทำ kubectl apply เหมือนเดิม + เพิ่มการ commit เข้า config repo
- Argo เปิด auto-sync ที่ dev
- เกณฑ์ผ่านเฟส: 2 สัปดาห์ที่ dev ไม่มี incident จากเรื่องนี้

## เฟส 3 (สัปดาห์ 5): ตัด kubectl ออกจาก dev
- ลบ step kubectl apply ออกจาก workflow ของ dev
- อบรมทีม 1 ชม.: อ่าน Argo UI, sync, rollback, ดู diff
- เกณฑ์ผ่านเฟส: ทุกคนในทีม rollback ผ่าน Argo ได้เอง

## เฟส 4 (สัปดาห์ 7-8): uat แล้วค่อย prod
- prod เปิดแค่ manual sync ก่อน 1 เดือน
- เปิด auto-sync ที่ prod ต่อเมื่อไม่มีปัญหาติดต่อกัน 1 เดือน

## เกณฑ์ย้อนกลับ (ทุกเฟส)
- Argo ทำให้เกิด incident ที่กระทบผู้ใช้ → กลับไปใช้ kubectl ทันที
- ทีมมากกว่าครึ่งบอกว่าทำงานช้าลงหลัง 2 สัปดาห์ → หยุดทบทวน

## ความเสี่ยงที่รู้อยู่แล้ว
- selfHeal จะดึงการแก้ด้วยมือกลับ → ต้องอบรมให้ชัดก่อนเปิด
- คนที่ชิน kubectl จะอึดอัดช่วงแรก
```

**เกณฑ์ผ่าน:** มี **เกณฑ์ย้อนกลับ** และ **แผนอบรม**
แผนย้ายเทคโนโลยีที่ไม่มีสองอย่างนี้มักล้มเหลว — ไม่ใช่เพราะเทคโนโลยี แต่เพราะคน

## C5.5 pipeline ที่เชื่อถือได้

หาสถิติ:

```bash
gh api "repos/:owner/:repo/actions/workflows/ci.yml/runs?per_page=100" \
  | jq -r '.workflow_runs[] | "\(.conclusion) \(.head_sha)"' \
  | sort | uniq -c
```

หา commit ที่รันหลายครั้งแล้วได้ผลต่างกัน = **flaky**

สาเหตุที่พบบ่อยและวิธีแก้:

| สาเหตุ | อาการ | แก้ |
| --- | --- | --- |
| เทสแย่ง DB กัน | พังเมื่อรันขนาน | ให้แต่ละ worker ใช้ schema แยก |
| `sleep` แทนการรอเงื่อนไข | พังบน runner ที่ช้า | เปลี่ยนเป็น poll จนกว่าจะพร้อม |
| ขึ้นกับเวลา/timezone | พังตอนเที่ยงคืน | ตรึงเวลาในเทส |
| ขึ้นกับลำดับการรัน | พังเมื่อสลับลำดับ | ล้าง state ใน `beforeEach` |
| เรียก network จริง | พังเมื่อเน็ตช้า | mock หรือใช้ testcontainers |

**ทำไมเรื่องนี้สำคัญกว่าที่คิด:**

```
CI แดงแบบสุ่ม → คนกด re-run → บางทีก็เขียว
             → สมองเรียนรู้ว่า "แดง = กด re-run"
             → วันที่แดงเพราะบั๊กจริง คนก็กด re-run แล้ว merge
             → CI กลายเป็นพิธีกรรมที่ไม่มีความหมาย
```

**pipeline ที่เชื่อถือไม่ได้ แย่กว่าไม่มี pipeline** เพราะมันให้ความมั่นใจปลอม ๆ

**เกณฑ์ผ่าน:** อัตราการ re-run ลดลงชัดเจน และมีตัวเลขยืนยัน

## C5.6 ควบคุมต้นทุน

```bash
gh api "repos/:owner/:repo/actions/workflows/ci.yml/timing"
```

เรียงตามผลลัพธ์ที่มักได้:

| วิธี | ประหยัดได้ | ข้อควรระวัง |
| --- | --- | --- |
| `concurrency: cancel-in-progress` | 20-40% | ห้ามใช้กับ job deploy |
| `paths` filter | 10-30% | ระวัง required check ที่ไม่มีวันมา |
| docker layer cache | 20-40% ของ job ที่ build | cache ของ GHA มีเพดาน 10GB |
| ตัด matrix ที่ไม่จำเป็น | ตามสัดส่วน | ต้องแน่ใจว่าไม่ต้อง support เวอร์ชันนั้นแล้ว |
| ใช้ Linux แทน macOS | **90%** | macOS คิดค่าใช้จ่าย 10 เท่า |

**ระวังการลดที่ทำลายคุณค่า:** ลดเวลาโดยตัดเทสออก = ประหยัดเงินแต่เพิ่มความเสี่ยง
เป้าหมายคือ **ลดเวลาที่เสียเปล่า** ไม่ใช่ลดการตรวจสอบ

## C5.7 platform docs

โครงที่ตอบครบ 5 คำถาม:

```markdown
# คู่มือนักพัฒนา: จากโค้ดถึง production

## 1. โค้ดของฉันเดินทางยังไง
[แผนภาพ] เครื่องคุณ → PR → CI → merge → build image → GHCR → deploy → production
เวลาโดยเฉลี่ย: 12 นาทีจาก merge ถึงขึ้นจริง

## 2. CI แดงต้องทำยังไง
1. เปิดแท็บ Actions หา step ที่แดง
2. ดูตารางอาการที่พบบ่อย [ลิงก์]
3. ยังแก้ไม่ได้ → ถามที่ #dev-help (มีคนดูตลอดเวลาทำการ)
⚠️ ห้ามกด re-run โดยไม่อ่าน error — ถ้าคิดว่า flaky ให้แจ้งใน #ci-flaky

## 3. deploy ยังไง
- dev: merge เข้า `dev` → ขึ้นเอง ไม่ต้องขออนุมัติ
- production: merge เข้า `main` → รออนุมัติจาก [ทีม]
- ตรวจสถานะได้ที่ [ลิงก์ Argo/Actions]

## 4. พังแล้วทำยังไง
1. แจ้ง #incident ก่อนเสมอ (แม้ยังไม่รู้สาเหตุ)
2. rollback: `git revert <commit>` แล้ว push (**ห้ามใช้ kubectl rollout undo** — Argo จะดึงกลับ)
3. รอ 3 นาที ตรวจ [ลิงก์ dashboard]

## 5. เพิ่มบริการใหม่ต้องทำอะไร
[เช็กลิสต์ 8 ข้อพร้อมลิงก์ template repo]

## เริ่มต้นวันแรก
- [ ] ขอสิทธิ์ [ลิงก์ฟอร์ม]
- [ ] clone repo แล้วรัน `make dev`
- [ ] แก้ข้อความอะไรก็ได้ 1 บรรทัด เปิด PR แล้ว deploy ขึ้น dev ให้สำเร็จ
```

**เกณฑ์ผ่านมีข้อเดียว: คนใหม่ deploy ได้เองภายในวันแรกโดยไม่ต้องถามใคร**

วิธีทดสอบเอกสาร: ให้คนใหม่ทำตามแล้ว**นั่งดูเงียบ ๆ** จดทุกจุดที่เขาสะดุดหรือหันมาถาม
ทุกคำถามที่เขาถาม = ช่องว่างในเอกสาร

**สัญญาณว่าเอกสารยังไม่ดีพอ:** มีคนถามคำถามเดิมใน chat ซ้ำ ๆ ทุกเดือน
