# 09 — จะตั้งค่าที่ชั้นไหนดี (คู่มือตัดสินใจ)

เอกสารนี้ตอบคำถามเดียว: **Load balancing, Rate limit, Health check ควรตั้งที่ Nginx, ที่ Kubernetes, หรือที่แอป?**

## ภาพรวม 5 ชั้นที่ traffic ต้องผ่าน

```
① CDN / WAF          Cloudflare, AWS WAF        ← ไกลผู้ใช้ที่สุด, รู้จักผู้ใช้น้อยที่สุด
② Edge proxy         Nginx / Ingress
③ Gateway / Mesh     Kong, Istio
④ Platform           Kubernetes Service, HPA, probe
⑤ Application        โค้ดของเราเอง               ← ใกล้ผู้ใช้น้อยที่สุด, รู้จักผู้ใช้มากที่สุด
```

**กฎ 3 ข้อที่ใช้ตัดสินใจได้เกือบทุกเคส**

1. **ยิ่งเป็นเรื่องปริมาณล้วน ๆ ยิ่งตั้งใกล้ผู้ใช้** — DDoS, bot, request ขยะ ควรตายตั้งแต่ชั้น ① หรือ ② อย่าปล่อยมากินทรัพยากรชั้นใน
2. **ยิ่งต้องรู้ว่า "ใคร" ยิ่งตั้งใกล้แอป** — quota ต่อผู้ใช้, ต่อ plan, ต่อ tenant ต้องอยู่ที่ ⑤ เพราะชั้นนอกไม่รู้จัก user id
3. **อย่าตั้งเรื่องเดียวกันสองชั้นโดยไม่ตั้งใจ** — ถ้าตั้งซ้ำ ต้องรู้ว่าแต่ละชั้นทำหน้าที่ต่างกันยังไง ไม่ใช่ทำซ้ำกัน

## 1. Load balancing — ตั้งที่ไหนดี

| ชั้น                 | เครื่องมือ    | ระดับ  | กระจายต่อ      | จุดแข็ง                                | จุดอ่อน                                                                   |
| -------------------- | ------------- | ------ | -------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| ② Nginx (compose/VM) | `upstream`    | L7     | request        | คุมได้ละเอียด, อัลกอริทึมเลือกได้      | active health check ต้องจ่ายเงิน, ต้องแก้ config เองเมื่อ backend เปลี่ยน |
| ④ K8s Service        | kube-proxy    | **L4** | **connection** | ฟรี, อัตโนมัติ, ตามจำนวน pod จริง      | **กระจาย gRPC/HTTP2 ไม่ได้**, ไม่มี retry ระดับ request                   |
| ② K8s Ingress        | ingress-nginx | L7     | request        | routing + TLS + sticky cookie ครบ      | ใช้กับ traffic ขาเข้าเป็นหลัก                                             |
| ③ Service Mesh       | Istio/Linkerd | L7     | request        | retry, circuit breaker, canary %, mTLS | ค่าดูแลสูงมาก, debug ยาก                                                  |

### เลือกยังไง

| สถานการณ์                                  | คำตอบ                                                                                         |
| ------------------------------------------ | --------------------------------------------------------------------------------------------- |
| รันบน VM ตัวเดียวด้วย docker compose       | **Nginx `upstream`** — ไม่มีทางเลือกอื่นและก็เพียงพอ                                          |
| รันบน k8s, REST API, traffic จากภายนอก     | **Ingress + Service** — ไม่ต้องมีอะไรเพิ่ม                                                    |
| รันบน k8s แต่เป็น **gRPC ระหว่าง service** | **Service Mesh** หรือ headless service + client-side LB — Service เฉย ๆ จะกระจุกที่ pod เดียว |
| ต้องการ canary 5% / circuit breaker        | **Service Mesh** (หรือ Argo Rollouts ถ้าไม่อยากลง mesh ทั้งก้อน)                              |
| มีแค่ 3-5 service คุยกันเอง                | **ยังไม่ต้องใช้ mesh** — ราคาแพงเกินประโยชน์ที่ได้                                            |

> **อย่าเอา nginx ของตัวเองไปวางหน้า Service บน k8s** — คุณจะได้ nginx ซ้อน nginx (เพราะ ingress ก็คือ nginx)
> timeout ซ้อนกันสองชั้น, log แยกกันสองที่, และไม่ได้อะไรเพิ่มเลย

## 2. Rate limit — ตั้งที่ไหนดี

| ชั้น                 | นับรวมข้ามเครื่อง | รู้จัก user    | ตัดก่อนถึงแอป     | ค่าดูแล            |
| -------------------- | ----------------- | -------------- | ----------------- | ------------------ |
| ① CDN / WAF          | ✅                | ⚠️             | ✅ ดีที่สุด       | ต่ำ (มีค่าใช้จ่าย) |
| ② Nginx / Ingress    | ❌ ต่อ replica    | ❌ รู้แค่ IP   | ✅                | ต่ำมาก             |
| ③ API Gateway        | ✅                | ✅ per API key | ✅                | กลาง               |
| ③ Service Mesh + RLS | ✅                | ✅             | ✅                | สูง                |
| ⑤ แอป + Redis        | ✅                | ✅ ละเอียดสุด  | ❌ โหลดถึงแอปแล้ว | ต่ำ                |

### สูตรที่ใช้ได้จริง — ทำสองชั้น

```
ชั้นขอบ (Nginx/Ingress): 100 r/s ต่อ IP    → "กันของขยะ" ตั้งหลวมไว้ ไม่ต้องแม่น
ชั้นแอป (Redis):         1,000 req/วัน/user → "quota จริง" ต้องแม่น เพราะเกี่ยวกับเงิน
```

เหตุผลที่ต้องแยก: ชั้นขอบเร็วและถูก แต่ **ไม่รู้ว่าใครเป็นใคร** ส่วนชั้นแอปรู้ทุกอย่างแต่การจะรู้ได้ต้องปล่อย request เข้ามาก่อน

### ⚠️ ปัญหาที่ทุกคนเจอ: limit ต่อ replica

ทั้ง `limit_req` ของ nginx และ `limit-rps` ของ ingress-nginx เก็บสถานะไว้ **ในหน่วยความจำของ process นั้น**

```
ตั้ง 10 r/s × ingress controller 3 replica = ผู้ใช้ยิงได้จริง 30 r/s
```

ถ้าจำนวน replica ขยับตาม HPA → limit จริงก็ขยับตาม โดยไม่มีใครสังเกต
**ถ้าตัวเลขนี้ต้องแม่น (เช่นเป็น SLA ที่ขายลูกค้า) ห้ามใช้ชั้น ② เด็ดขาด** ต้องขึ้นไปใช้ ③ หรือ ⑤ ที่มีที่เก็บสถานะกลาง

## 3. Health check — ตั้งที่ไหนดี

| ชั้น                   | ความสามารถ                                      | active? | แยก "ฆ่า" กับ "ถอดออกจาก pool" ได้ไหม |
| ---------------------- | ----------------------------------------------- | ------- | ------------------------------------- |
| ② Nginx OSS            | `max_fails` / `fail_timeout` (passive)          | ❌      | ❌ ทำได้แค่พัก backend ชั่วคราว       |
| ② Nginx Plus           | `health_check`                                  | ✅      | ❌                                    |
| ④ **Kubernetes probe** | liveness / readiness / startup                  | ✅      | ✅ **แยกได้ชัดเจน**                   |
| ③ Service Mesh         | outlier detection (ตัด pod ที่ตอบ error ถี่ออก) | ✅      | ✅                                    |

**ข้อสรุปตรงนี้ไม่มีข้อโต้แย้ง: ถ้าอยู่บน Kubernetes ให้ใช้ probe ของ k8s เป็นหลักเสมอ**
เพราะมันเป็นชั้นเดียวที่แยกได้ว่า "อาการนี้ควร restart" กับ "อาการนี้แค่หยุดส่งงานให้"

แต่ยังต้องทำที่ชั้นอื่นด้วยในบางเรื่อง:

| เรื่อง                                 | ทำที่                           | เพราะ                                                         |
| -------------------------------------- | ------------------------------- | ------------------------------------------------------------- |
| ตัด pod ที่ยังไม่พร้อมออกจาก LB        | ④ readinessProbe                | k8s อัปเดต Service endpoint ให้อัตโนมัติ                      |
| restart แอปที่ค้าง                     | ④ livenessProbe                 | ชั้นอื่นทำแทนไม่ได้                                           |
| ไม่ตัด request ที่ค้างตอน pod กำลังดับ | ⑤ **ในแอป** (`SIGTERM` handler) | k8s ส่งสัญญาณให้ได้ แต่ปิดงานให้เรียบร้อยเป็นหน้าที่ของแอปเอง |
| ตัด backend ที่ตอบ 5xx ถี่ ๆ ทันที     | ③ mesh outlier detection        | probe อาจยังผ่านอยู่ทั้งที่ตอบ error                          |

**สิ่งที่ k8s ทำแทนเราไม่ได้เลย** คือ endpoint ที่บอกความจริง — ถ้า `/readyz` คืน 200 ตลอดโดยไม่เช็คอะไร probe ทั้งระบบก็ไร้ความหมาย

## 4. Timeout — ต้องตั้งให้ "ชั้นในสั้นกว่าชั้นนอก"

นี่คือเรื่องที่คนตั้งผิดกันมากที่สุดและเจ็บที่สุด

```
Browser        30s
  └ Ingress    25s     ← แต่ละชั้นต้องสั้นลงเรื่อย ๆ
     └ Service —
        └ App  20s
           └ HTTP call ออกไปข้างนอก  10s
              └ DB query               5s
```

ถ้าตั้งกลับด้าน (เช่น app timeout 60s แต่ ingress 30s) จะเกิดอาการนี้:
ingress ตัด connection ที่ 30s ผู้ใช้เห็น 504 → **แต่แอปยังทำงานต่ออีก 30 วิโดยไม่มีใครรออยู่แล้ว**
= เปลือง connection pool, เปลือง DB connection, และตอนโหลดสูงจะกลายเป็นหิมะถล่ม

**กฎ: timeout ของชั้นใน ต้องน้อยกว่าชั้นนอกเสมอ อย่างน้อย 20%**

## 5. Retry — ตั้งได้ที่เดียวเท่านั้น

```
Ingress retry 3 ครั้ง × Mesh retry 3 ครั้ง × App retry 3 ครั้ง = 27 requests จาก 1 request
```

นี่คือ **retry storm** — ระบบที่ช้าอยู่แล้วจะโดนซ้ำเป็น 27 เท่าจนตายสนิท

| กฎ                    | รายละเอียด                                                                      |
| --------------------- | ------------------------------------------------------------------------------- |
| retry ชั้นเดียวพอ     | เลือกชั้นที่ใกล้ปัญหาที่สุด ปกติคือชั้นที่เรียก dependency นั้นโดยตรง           |
| retry เฉพาะที่ปลอดภัย | GET/PUT/DELETE (idempotent) เท่านั้น — POST ที่ไม่ idempotent อาจสร้างข้อมูลซ้ำ |
| ใส่ backoff + jitter  | retry ทันทีพร้อมกันทุก client = ถล่มซ้ำเป็นจังหวะ                               |
| มี circuit breaker    | พังเกินเกณฑ์ให้หยุดยิงไปเลยสักพัก ดีกว่าค่อย ๆ ตายด้วยกัน                       |

## ตารางสรุปสุดท้าย — ถ้าจำได้แค่หน้าเดียว จำหน้านี้

| เรื่อง                       | อยู่บน VM + Compose                       | อยู่บน Kubernetes                                                   |
| ---------------------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| **Load balance**             | Nginx `upstream` (round-robin พอ)         | Service + Ingress; ใช้ mesh เฉพาะตอนมี gRPC ภายในหรือต้องการ canary |
| **Rate limit หยาบ**          | Nginx `limit_req`                         | Ingress annotation                                                  |
| **Rate limit ตาม quota**     | ในแอป + Redis                             | ในแอป + Redis (เหมือนกัน)                                           |
| **Restart เมื่อแอปค้าง**     | `restart: unless-stopped` + `HEALTHCHECK` | **livenessProbe**                                                   |
| **หยุดส่ง traffic ชั่วคราว** | ทำได้ไม่ดี (`max_fails` แบบ passive)      | **readinessProbe**                                                  |
| **แอป boot ช้า**             | `start_period` ของ HEALTHCHECK            | **startupProbe**                                                    |
| **Scale ตามโหลด**            | ทำมือ (`--scale`)                         | **HPA**                                                             |
| **TLS**                      | certbot + mount cert                      | **cert-manager**                                                    |
| **Graceful shutdown**        | จัดการ SIGTERM ในแอป                      | จัดการ SIGTERM ในแอป (เหมือนกัน — ไม่มีใครทำแทนได้)                 |

## เช็กลิสต์ก่อนขึ้น production

- [ ] `/healthz` **ไม่** แตะ database
- [ ] `/readyz` แตะเฉพาะ dependency ที่จำเป็นจริง ๆ และไม่เรียกต่อไปยัง service อื่นเป็นทอด
- [ ] liveness ตั้งใจเย็นกว่า readiness (period ยาวกว่า, threshold สูงกว่า)
- [ ] health check endpoint ไม่ติด rate limit
- [ ] timeout ไล่จากชั้นนอกมาชั้นใน สั้นลงเรื่อย ๆ
- [ ] retry เปิดไว้ชั้นเดียว มี backoff + jitter
- [ ] รู้ว่า rate limit ที่ตั้งไว้เป็น "ต่อ replica" หรือ "ทั้งระบบ"
- [ ] แอปจัดการ SIGTERM และปิด connection ที่ค้างให้เรียบร้อย
- [ ] ทุก container มี `resources.requests` และ `limits`
- [ ] ทดสอบ rolling update จริงแล้วไม่เจอ 502/503 สักตัว
